## Why Railway Works Well

<Card title="Railway Platform" icon="rocket">
Railway gives Git-triggered builds, IPv6 private networking, and automatic TLS for public services. LeafLock’s frontend runs publicly while the backend stays private.
</Card>

**Services created** inside one Railway project:

- `leaflock-backend` (private service, no domain)
- `leaflock-frontend` (public domain)
- PostgreSQL plugin (managed database)
- Redis plugin (managed cache + rate limiter)

## Step 1 – Provision Secrets

Set strong values before first deploy. Railway injects them at build and runtime.

<Code
  code={`openssl rand -base64 64  # JWT_SECRET
openssl rand -base64 32  # SERVER_ENCRYPTION_KEY
openssl rand -base64 32  # DEFAULT_ADMIN_PASSWORD

# Railway UI → Backend → Variables
JWT_SECRET=<value>
SERVER_ENCRYPTION_KEY=<value>
DEFAULT_ADMIN_EMAIL=ops@yourdomain.com
DEFAULT_ADMIN_PASSWORD=<value>
ENABLE_REGISTRATION=false`}
  language="bash"
/>

<Aside type="caution">
Do not reuse `.env.example` values—the backend exits immediately if it detects weak secrets.
</Aside>

## Step 2 – Configure Backend Service

- Root directory: `/backend`
- Deployment type: Dockerfile (auto-detected)
- Disable public domain (private-only)

<Code
  code={`DATABASE_URL=$RAILWAY_POSTGRES_URL
POSTGRES_PASSWORD=$RAILWAY_POSTGRES_PASSWORD
REDIS_URL=$RAILWAY_REDIS_URL
REDIS_PASSWORD=$RAILWAY_REDIS_PASSWORD
JWT_SECRET=<from secrets>
SERVER_ENCRYPTION_KEY=<from secrets>
APP_ENV=production
CORS_ORIGINS=https://leaflock-frontend-production.up.railway.app
ENABLE_METRICS=true
ENABLE_DEFAULT_ADMIN=true`}
  language="bash"
/>

The Go server binds to `[::]:8080` (`backend/server/listener.go`) so Railway IPv6 networking works out of the box.

## Step 3 – Configure Frontend Service

- Root directory: `/frontend`
- Port: `80`
- Assign Railway public domain (e.g., `leaflock-frontend-production.up.railway.app`)

### How Dynamic Configuration Works

The frontend automatically detects Railway services using this priority order:

1. **`VITE_API_URL`** (explicit override - highest priority)
2. **`BACKEND_URL`** (Railway automatic service variable)
3. **`RAILWAY_INTERNAL_HOST`** (Railway private hostname) ⭐ **Preferred**
4. **`RAILWAY_PRIVATE_DOMAIN`** (Railway private domain) ⭐ **Preferred**
5. Service name patterns (`backend`, `api`, `server`)
6. **`RAILWAY_PUBLIC_DOMAIN`** (fallback)

<Aside type="tip">
Set `VITE_SHOW_CONFIG=true` to see the resolved configuration in a debug panel on your frontend. This helps troubleshoot connection issues.
</Aside>

<Code

## Dynamic Configuration System

LeafLock includes an intelligent configuration system that automatically detects Railway services and uses private hostnames for optimal security and performance.

### How It Works

The frontend automatically resolves the backend API URL using this priority:

1. **`VITE_API_URL`** - Explicit override (highest priority)
2. **`BACKEND_URL`** - Railway automatic service variable
3. **`RAILWAY_INTERNAL_HOST`** - Railway private hostname ⭐ **Preferred**
4. **`RAILWAY_PRIVATE_DOMAIN`** - Railway private domain ⭐ **Preferred**
5. Service name patterns (`backend`, `api`, `server`)
6. **`RAILWAY_PUBLIC_DOMAIN`** - Fallback

### Benefits

- **🔒 Security**: Uses Railway's private IPv6 networking
- **⚡ Performance**: No external DNS lookups
- **🔄 Automatic**: No manual configuration needed
- **🐛 Debuggable**: Debug panel shows resolved configuration

### Debug Mode

Set `VITE_SHOW_CONFIG=true` to enable a debug panel that shows:
- Resolved API URL
- Platform detection (Railway vs local)
- Environment variables
- Service discovery status

This helps troubleshoot connection issues and verify the configuration is working correctly.

## Custom Domain Checklist

- Add domain under frontend → Settings → Domains.
- Point DNS `CNAME` to the Railway hostname.
- Update backend `CORS_ORIGINS` to include the new domain.
- Toggle `ENABLE_REGISTRATION` based on whether sign-ups should be public.

## PR Preview Deployments

Railway automatically creates PR preview environments for each pull request. LeafLock is pre-configured for this:

**Backend**: `backend/railway.toml` sets `APP_ENV=development` to auto-allow `*.railway.app` CORS origins.

**Frontend**: **Do NOT set `VITE_API_URL`** in Railway environment variables. The frontend automatically discovers the PR backend via Railway's service discovery using private hostnames.

**Common Issue**: If PR frontend shows CORS errors connecting to production backend (`https://leaflock.app`), remove `VITE_API_URL` from Railway environment variables and redeploy. The dynamic configuration will automatically use the correct PR backend.

<Aside type="tip">
PR previews work seamlessly with the dynamic configuration system. Each PR gets its own backend service, and the frontend automatically connects to it using Railway's private networking.
</Aside>

## Troubleshooting

- **502 from frontend** → Check Railway logs for connection errors. The dynamic configuration should automatically resolve the backend URL.
- **Backend crash loops** → secrets missing; check Railway logs for `FATAL` messages from `config.LoadConfig`.
- **WebSocket disconnects** → Railway load balancer requires sticky sessions; enable them in service settings.
- **Slow first request** → backend warms caches on boot (templates, admin, allowlist). Wait for readiness to report `status=ready`.
- **CORS errors** → Remove `VITE_API_URL` from Railway environment variables. The dynamic configuration will use Railway's private networking.
- **API connection issues** → Set `VITE_SHOW_CONFIG=true` and check the debug panel to see which API URL is being used.

<Aside type="tip">
The dynamic configuration system eliminates most connection issues by automatically detecting Railway services. If you're having problems, check the debug panel first.
</Aside>

<Aside type="caution">
Never assign a public domain to the backend service—doing so bypasses CSRF protection and exposes raw APIs to the internet.
</Aside>
