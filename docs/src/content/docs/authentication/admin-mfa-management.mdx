# Admin MFA Management (Clerk)

This guide is for system administrators who need to manage MFA settings or assist users with account access issues when using Clerk authentication.

## Understanding Clerk MFA Management

With Clerk, MFA management is primarily handled through:

1. **Clerk Dashboard** - Web interface for user management
2. **Clerk API** - Programmatic access for automation
3. **LeafLock Admin Interface** - Custom admin features
4. **Database-level** - For emergency access and reporting

## Clerk Dashboard Management

### Accessing the Clerk Dashboard

1. Log in to [Clerk Dashboard](https://dashboard.clerk.com)
2. Select your LeafLock application
3. Navigate to **Users** section

### User MFA Management via Dashboard

#### View User MFA Status
1. Search for the user by email or user ID
2. Click on the user profile
3. Go to **Security** tab
4. View MFA status and methods

#### Reset User MFA
1. Find the user in the dashboard
2. Click **More Actions** → **Reset MFA**
3. Confirm the reset operation
4. User will receive notification about the reset

#### Disable MFA for User
1. Navigate to user profile
2. Go to **Security** settings
3. Toggle **Two-factor authentication** to **Off**
4. Confirm the change

### Bulk Operations via Dashboard

Clerk dashboard supports bulk operations:
1. Select multiple users with checkboxes
2. Use **Bulk Actions** menu
3. Apply MFA settings to selected users

## API-Based MFA Management

### Using Clerk API for Automation

#### Reset MFA via API

```bash
# Reset MFA for a specific user
curl -X POST \
  "https://api.clerk.com/v1/users/{USER_ID}/mfa" \
  -H "Authorization: Bearer {CLERK_SECRET_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "disabled": true
  }'
```

#### Get User MFA Status

```bash
# Get user MFA information
curl -X GET \
  "https://api.clerk.com/v1/users/{USER_ID}/mfa" \
  -H "Authorization: Bearer {CLERK_SECRET_KEY}"
```

#### List Users with MFA Enabled

```bash
# Get all users with MFA enabled
curl -X GET \
  "https://api.clerk.com/v1/users?query=mfa_enabled:true" \
  -H "Authorization: Bearer {CLERK_SECRET_KEY}"
```

## Database-Level MFA Reporting

While Clerk manages MFA state, you can query the database for reporting and analytics.

### User MFA Status Queries

#### Find All Users with MFA Enabled (Clerk)

```sql
-- Users with Clerk MFA enabled (via metadata)
SELECT
  u.id,
  u.email_encrypted,
  u.is_admin,
  u.created_at,
  u.last_login,
  CASE 
    WHEN u.clerk_user_id IS NOT NULL THEN 'clerk'
    ELSE 'legacy'
  END as auth_type
FROM users u
WHERE u.clerk_user_id IS NOT NULL
  AND u.deleted_at IS NULL
ORDER BY u.last_login DESC NULLS LAST;
```

#### MFA Adoption Statistics

```sql
-- Overall authentication method distribution
SELECT
  CASE 
    WHEN clerk_user_id IS NOT NULL THEN 'Clerk'
    ELSE 'Legacy JWT'
  END as auth_method,
  COUNT(*) as user_count,
  ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) as percentage
FROM users
WHERE deleted_at IS NULL
GROUP BY auth_method
ORDER BY user_count DESC;

-- Admin users by authentication method
SELECT
  CASE 
    WHEN clerk_user_id IS NOT NULL THEN 'Clerk'
    ELSE 'Legacy JWT'
  END as auth_method,
  COUNT(*) as admin_count
FROM users
WHERE is_admin = true
  AND deleted_at IS NULL
GROUP BY auth_method;
```

### Security Monitoring Queries

```sql
-- Admin accounts that may need MFA enforcement
SELECT
```

#### Recently Active Users (For MFA Audit)

```sql
-- Users active in last 30 days with auth type
SELECT
  u.id,
  u.email_encrypted,
  u.last_login,
  CASE 
    WHEN u.clerk_user_id IS NOT NULL THEN 'Clerk'
    ELSE 'Legacy JWT'
  END as auth_method,
```

## Emergency User Recovery

### Complete Account Recovery Process

#### Step 1: Verify User Identity
Before performing any recovery operations:

1. **Official Communication**: Verify request through company email/phone
2. **Personal Verification**: Ask security questions
3. **Manager Approval**: Get approval from user's manager (for corporate accounts)
4. **Document Everything**: Record the recovery request and approval

#### Step 2: Reset MFA via Clerk Dashboard
1. Log into Clerk Dashboard
2. Find the user by email
3. Go to **Security** tab
4. Click **Reset MFA**
5. Confirm the operation
6. Note the timestamp for audit log

#### Step 3: Alternative - API Reset
For automated systems or bulk operations:

```bash
# Reset MFA for user
curl -X POST \
  "https://api.clerk.com/v1/users/{USER_ID}/mfa" \
  -H "Authorization: Bearer {CLERK_SECRET_KEY}" \
  -d '{"disabled": true}'

# Force password reset (recommended)
curl -X POST \
  "https://api.clerk.com/v1/users/{USER_ID}/password" \
  -H "Authorization: Bearer {CLERK_SECRET_KEY}" \
  -d '{"password": "temporary_password_123", "require_password_change": true}'
```

#### Step 4: Notify User
Send comprehensive instructions:

```
Subject: MFA Reset Complete - Action Required

Your MFA has been reset for security reasons.

Next Steps:
1. Log in with your email and password only
2. Immediately re-enable MFA in your profile settings
3. Set up your preferred authentication method
4. Generate and save new backup codes
5. Review your recent account activity

Security Recommendations:
- Use a different authenticator app/device
- Update your backup code storage
- Consider enabling additional security features

If you didn't request this reset, contact support immediately.
```

### Account Lockout Recovery

#### Check Lockout Status
```sql
-- Check if user is locked out (Clerk manages this, but check audit logs)
SELECT
  al.created_at,
  al.action,
  al.ip_address_encrypted,
  al.metadata_encrypted
FROM audit_log al
WHERE al.user_id = 'USER_ID_HERE'
  AND al.action IN ('login.failed', 'account.locked', 'account.unlocked')
ORDER BY al.created_at DESC
LIMIT 10;
```

#### Unlock Account (if needed)
```bash
# Unlock user account via Clerk API
curl -X POST \
  "https://api.clerk.com/v1/users/{USER_ID}/unlock" \
  -H "Authorization: Bearer {CLERK_SECRET_KEY}"
```

## Bulk Operations and Automation

### Batch User MFA Status Check

```python
import requests
import os

CLERK_SECRET_KEY = os.getenv('CLERK_SECRET_KEY')
CLERK_API_URL = "https://api.clerk.com/v1"

def check_user_mfa_status(user_id):
    """Check MFA status for a single user"""
    headers = {"Authorization": f"Bearer {CLERK_SECRET_KEY}"}
    
    response = requests.get(
        f"{CLERK_API_URL}/users/{user_id}/mfa",
        headers=headers
    )
    
    if response.status_code == 200:
        return response.json()
    else:
        return None

def get_users_with_mfa():
    """Get all users with MFA enabled"""
    headers = {"Authorization": f"Bearer {CLERK_SECRET_KEY}"}
    
    response = requests.get(
        f"{CLERK_API_URL}/users?limit=500",
        headers=headers
    )
    
    users_with_mfa = []
    if response.status_code == 200:
        users = response.json().get('data', [])
        for user in users:
            if user.get('two_factor_enabled'):
                users_with_mfa.append(user)
    
    return users_with_mfa

# Example usage
users_with_mfa = get_users_with_mfa()
print(f"Found {len(users_with_mfa)} users with MFA enabled")
```

### Automated MFA Compliance Report

```sql
-- Generate MFA compliance report
SELECT
  DATE(u.created_at) as registration_date,
  COUNT(*) as total_users,
  COUNT(*) FILTER (WHERE u.clerk_user_id IS NOT NULL) as clerk_users,
  COUNT(*) FILTER (WHERE u.clerk_user_id IS NULL) as legacy_users,
  COUNT(*) FILTER (WHERE u.is_admin = true) as admin_users,
  COUNT(*) FILTER (WHERE u.last_login > NOW() - INTERVAL '30 days') as active_users
FROM users u
WHERE u.deleted_at IS NULL
GROUP BY DATE(u.created_at)
ORDER BY registration_date DESC
LIMIT 30;
```

## Security Monitoring and Alerts

### Suspicious Activity Detection

```sql
-- Users with multiple failed login attempts (potential attack)
SELECT
  al.user_id,
  COUNT(*) as failed_attempts,
  MAX(al.created_at) as last_attempt,
  al.ip_address_encrypted
FROM audit_log al
WHERE al.action = 'login.failed'
  AND al.created_at > NOW() - INTERVAL '1 hour'
GROUP BY al.user_id, al.ip_address_encrypted
HAVING COUNT(*) >= 5
ORDER BY failed_attempts DESC;
```

### Admin Activity Monitoring

```sql
-- Recent admin actions
SELECT
  al.created_at,
  al.user_id,
  al.action,
  al.metadata_encrypted,
  al.ip_address_encrypted
FROM audit_log al
WHERE al.action LIKE 'admin.%'
  AND al.created_at > NOW() - INTERVAL '24 hours'
ORDER BY al.created_at DESC;
```

## Emergency Procedures

### Mass Security Incident Response

In case of security breach affecting MFA:

1. **Immediate Assessment**
   ```sql
   -- Check for unusual MFA activity
   SELECT COUNT(*) as suspicious_events
   FROM audit_log
   WHERE action IN ('mfa.verification_failed', 'mfa.backup_code_failed')
     AND created_at > NOW() - INTERVAL '1 hour';
   ```

2. **Communication**
   - Notify security team
   - Prepare user communications
   - Document incident timeline

3. **Selective Response**
   - Reset MFA for affected users
   - Force password resets
   - Review access logs

## Clerk-Specific Considerations

### Dashboard vs API
- **Dashboard**: Best for individual user management
- **API**: Best for automation and bulk operations
- **Both**: Require proper authentication and authorization

### User Privacy
- Clerk manages user data securely
- Admins can see metadata but not sensitive data
- All actions are logged for compliance
- Follow data protection regulations

### Cross-Application Consistency
- MFA settings apply to all Clerk-enabled apps
- Changes affect user's entire Clerk ecosystem
- Consider impact before making changes
